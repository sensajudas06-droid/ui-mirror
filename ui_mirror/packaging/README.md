# Windows release build

From the repository root, run `./ui_mirror/packaging/build.ps1 -SkipPortable` for Setup only, or omit the switch to also build the portable executable. From inside `ui_mirror/`, the equivalent command is `./packaging/build.ps1 -SkipPortable`. Python 3.13 x64 and NSIS are required. Build output is written to `ui_mirror/dist/` relative to the repository root.

The script creates `build/venv`, installs the exact packages in `requirements-build.lock` with SHA-256 verification, runs `pip check`, and rejects an environment containing undeclared packages. It writes dependency versions, the lock hash, and artifact hashes to `dist/build-manifest.json`. The lock covers Windows x64 / CPython 3.13 wheels; it does not promise byte-identical executables across different toolchains or timestamps.

Native dependency collection is also isolated. During the build, `PATH` contains only the selected venv, its base Python installation and DLL directory, and Windows system directories. Inherited `PYTHONPATH`, `PYTHONHOME`, `TCL_LIBRARY`, and `TK_LIBRARY` are removed rather than set to empty strings; Python commands use isolated mode (`-I`). PyInstaller's own isolated Tcl/Tk probe and data directory checks must pass before packaging, because an empty Tcl variable can break discovery even when a direct Python import succeeds. All five environment variables are restored when the script exits, including on failure, preserving absent and empty values. NSIS is invoked by its absolute path.

`verify_native_inputs.py` checks the actual PyInstaller `Analysis-00.toc` after each application build, before the installer is produced. Every native source must resolve inside the active venv, base Python installation, or Windows System32 directory; missing files, relative paths, paths escaping through links, and unexpected native origins fail the release. It does not replace or arbitrarily exclude DLLs. Source paths and SHA-256 hashes are written to `dist/native-inputs-onedir.json`, `dist/native-inputs-portable.json` when built, and the release manifest.

This guard addresses a reproduced build contamination issue: the 1.9.9 portable executable included 43 Microsoft-signed native runtime files from an unrelated Codex `libheif` directory inherited through `PATH`. Their bytes matched the local originals; this was an unintended dependency source, not evidence of malware or proof of an antivirus detection cause. Approved paths and hashes improve traceability but do not establish upstream authenticity or guarantee any antivirus verdict.

The Requests baseline is 2.34.2. Earlier releases included Requests 2.31.0, which is affected by [CVE-2024-47081](https://github.com/psf/requests/security/advisories/GHSA-9hjg-9r4m-mvj7). This dependency fix is independent of antivirus verdicts.

Pillow is pinned to 13.0.0, which includes the [13.0 security fixes](https://pillow.readthedocs.io/en/stable/releasenotes/13.0.0.html). The app currently decodes fixed bundled image assets; no downloaded-image decoding path was found in the audit.

`generate_installer_manifest.py` records the exact payload and generates nonrecursive uninstall cleanup. Installer and uninstaller check the product/path/payload marker and reject reparse points before writing or deleting payload paths. Unknown files are retained. Shared registration is removed only by the registered active install; desktop shortcut cleanup additionally requires a creation record. Legacy 1.9.8 and earlier nonempty install directories have no marker and require a new/empty target. No automatic legacy uninstaller or migration runs.

A nonempty installation directory can be reused only to repair the exact same payload ID. A different package requires a new or empty target directory, even when its product marker is valid. Overlaying a changed payload would leave retired DLLs/files behind and then replace the ownership marker, making those old files unknown to the new exact uninstaller. The installer rejects that transition before writing payload files. It does not automatically uninstall or migrate an older installation; unrelated user files remain untouched.

`requirements-build.in` records direct build inputs. To update the lock, resolve those inputs in a fresh environment, download the resulting wheels from official PyPI, and record each exact version and wheel SHA-256. Review the changes and run the application tests before packaging. Application packages come from the dedicated venv; standard-library and Python runtime files come from its selected base Python installation.
